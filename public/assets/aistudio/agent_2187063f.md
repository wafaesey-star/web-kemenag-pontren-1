# AGENT.md — Panduan Agen Pengembangan

**Proyek: Sistem Pendataan Pondok Pesantren Tingkat Kabupaten**

Dokumen ini mengatur cara agen (AI/dev agent) bekerja pada proyek ini. Baca seluruh file ini sebelum melakukan perubahan kode.

---

## 1. Konteks Produk

Sistem web terpusat untuk pendataan pondok pesantren di tingkat kabupaten, dimiliki Kementerian Agama (Kemenag) Kabupaten. Rujukan kebutuhan: `prd.md`. Dokumen sumber awal: draft kebutuhan awal (lihat arsip dokumen).

Tiga peran pengguna: **Super Admin/Kemenag**, **Operator Pesantren** (terbatas pada pesantren yang ditugaskan), **Public** (opsional, hanya direktori & peta).

---

## 2. Prinsip Kerja

1. **Kebutuhan client belum final** — 10 open questions di `prd.md` §10 belum terjawab. Saat implementasi menyentuh area yang belum dikonfirmasi (field wajib, integrasi EMIS, multi-operator-per-pesantren, historis tahun ajaran), **buat konfigurabel** dan **catat keputusan asumsi** di `docs/assumptions.md`. Jangan mengunci desain ke satu asumsi.
2. **Prioritaskan MVP** — kerjakan fitur prioritas tinggi dulu (lihat `prd.md` §7). Jangan mengerjakan fitur prioritas rendah (direktori publik, notifikasi email/WA, mobile app) tanpa instruksi eksplisit.
3. **Kemenag = verifier tunggal.** Semua alur status data harus berpusat pada persetujuan Kemenag.
4. **Operator tidak pernah lepas** dari pembatasan: hanya pesantren yang ditugaskan, tidak bisa membuat pesantren baru, tidak bisa melihat pesantren lain. Setiap fitur untuk operator wajib menerapkan guard ini di level backend, bukan hanya UI.
5. **Data legalitas sensitif** — dokumen IJOP hanya boleh diakses Kemenag dan operator pesantren terkait.

## 4. Aturan Teknis

### 4.1 Backend
- Terapkan RBAC di middleware/decorator setiap endpoint, bukan per-route manual yang tersebar.
- Query data selalu difilter by scope: untuk role `operator`, paksa filter `pesantren_id` miliknya di lapisan repository/service.
- Audit log minimal mencatat: siapa, kapan, aksi apa, objek apa, nilai lama→baru (untuk perubahan data penting dan penugasan operator).
- Workflow status data: `draft → diajukan → diverifikasi → disetujui / ditolak`. Penolakan wajib menyimpan `catatan_revisi`. Penolakan mengembalikan data ke status `draft` (perbaikan) — sesuai §9 open question #10, edit pasca-approval belum final; gunakan flag konfigurasi.
- Semua endpoint mutasi (POST/PUT/PATCH/DELETE) validasi input dan kembalikan pesan error jelas & spesifik field.

### 4.2 Frontend
- Responsif (mobile + desktop), form dibuat sederhana dengan indikator progres pengisian.
- Gunakan open-source map (Leaflet + OpenStreetMap) untuk modul peta.
- Tampilkan status verifikasi dengan jelas (badge warna + catatan revisi jika ditolak).
- Pesan error harus menjelaskan *apa* yang salah dan *bagaimana* memperbaikinya.

### 4.3 Skema Data (inti, MVP)
Tabel minimal: `users` (+role), `pesantren`, `operator_assignments` (riwayat penugasan), `legalitas` (nomor, terbit, berakhir, status, dokumen, riwayat), `data_santri` (per periode/tahun ajaran), `tenaga_pendidik`, `sarpras`, `verifikasi_logs`, `audit_logs`.
- Gunakan kolom `periode`/`tahun_ajaran` sejak awal pada data kuantitatif (santri, pendidik, sarpras) untuk antisipasi open question #9.
- Simpan riwayat legalitas dan riwayat penugasan operator sebagai tabel terpisah (append-only).

## 5. Definisi Selesai (DoD)

Sebuah fitur dianggap selesai jika:
- [ ] Fungsionalitas sesuai `prd.md` (bagian prioritas MVP)
- [ ] Otorisasi role & scope pesantren diuji (termasuk negative test: operator akses pesantren lain harus ditolak)
- [ ] Validasi input & pesan error jelas
- [ ] Audit log tercatat untuk aksi penting
- [ ] UI responsif di ukuran HP dan laptop
- [ ] Catatan keputusan ditulis di `docs/assumptions.md` jika menyentuh open question
- [ ] Tidak ada secret/credential tertanam di kode

---

## 6. Larangan

- Jangan mengimplementasikan fitur prioritas rendah/opsional tanpa diminta.
- Jangan menambahkan integrasi eksternal (EMIS pusat, email/WA gateway) sebelum ada keputusan resmi.
- Jangan membypass pembatasan scope operator di endpoint mana pun.
- Jangan mengubah workflow verifikasi tanpa mencatat alasannya di `docs/assumptions.md`.
- Jangan commit data contoh yang berisi data pribadi nyata (gunakan data dummy/fiktif).

---

## 7. Checklist Sebelum Submit Perubahan

1. Jalankan test & linting.
2. Verifikasi guard akses operator (positive & negative test).
3. Pastikan migrasi DB reversible.
4. Update `docs/assumptions.md` bila ada keputusan baru.
5. Pastikan tidak ada data sensitif di log/git history.
